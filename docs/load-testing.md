# Load Testing

How to generate load against a workload in this cluster.

## Running a Load Test

podinfo has an [HPA](../manifests/podinfo/podinfo-hpa.yaml) that will scale the deployment on CPU load.

Trigger a run:

```bash
kubectl create job --from=cronjob/k6-loadtest k6-loadtest-manual -n podinfo
```

Watch it scale:

```bash
kubectl get hpa -n podinfo -w
```

## Pattern

Load is generated by a suspended `CronJob` running [k6](https://grafana.com/docs/k6/latest/), with the test script in a `ConfigMap` mounted into the pod. `suspend: true` means it never runs on its own, the `schedule` field is ignored while suspended.

A plain `Job` would work once, but ArgoCD won't recreate it after it completes. A suspended `CronJob` stays re-triggerable with the one command above.

See [`manifests/podinfo/k6-loadtest-cronjob.yaml`](../manifests/podinfo/k6-loadtest-cronjob.yaml) and [`manifests/podinfo/k6-loadtest-script.yaml`](../manifests/podinfo/k6-loadtest-script.yaml) for a working example.

The target workload's `CiliumNetworkPolicy` needs an ingress allow-rule for the k6 pod, or the requests never reach it. See [network-policies.md](https://github.com/ConsciousML/terragrunt-template-catalog-eks/blob/main/docs/network-policies.md) in the catalog repo.

## When to Reach for KEDA Instead

HPA on CPU covers request-rate scaling for a workload with live requests to measure. Reach for [KEDA](https://keda.sh/) instead when a workload is queue, cron, or event-driven, with no live request to measure.

KEDA isn't deployed in this cluster ([`charts/monitoring/prometheus-rules/keda.yaml`](../charts/monitoring/prometheus-rules/keda.yaml) keeps a ready-to-use alerting reference, commented out), only Karpenter handles autoscaling today. Adopting it means installing the KEDA operator first.
